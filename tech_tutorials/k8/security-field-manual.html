Kubernetes security is a continuous practice, not a one-time configuration. This manual walks through the architecture, the hardening decisions, and the automation that turn a default cluster into one you can put real workloads on.

Seven modules, in order: how the cluster actually works, the principles behind the controls, the hardening choices themselves, where AI changes the threat model, the benchmarks auditors check, the automation that enforces all of it, and a working dashboard mockup you can lift directly.

Why does Kubernetes exist?

Before you look at a single YAML file, it helps to know what problem this whole system is solving. No jargon in this section — just the shape of the idea.

What changes when a server crashes

Without an orchestrator

A server crashes at 2am. It stays down until a human notices and fixes it by hand.

With Kubernetes

Kubernetes notices immediately and replaces it — usually before anyone's paged.

That's the core value proposition. Everything else in this manual is about doing that safely, at scale, without opening new holes in the process.

Glossary: ten terms you'll see everywhere

A quick visual pass before the deep dive. Keep this open in another tab — look a term up here the first time it feels unfamiliar, whether you're twelve or forty-two.

Pod

The smallest thing Kubernetes runs — usually one container, sometimes a couple that share resources.

Namespace

A labeled area inside the cluster that keeps one team's or app's stuff separate from another's.

RBAC

Role-Based Access Control — the rulebook for who's allowed to do what in the cluster.

NetworkPolicy

A rule that says which pods are allowed to talk to which other pods.

Admission controller

A checkpoint that inspects a request and can reject or modify it before it's saved.

Pod Security Standards

Three preset safety levels for pods — Privileged, Baseline, and Restricted — from loosest to strictest.

mTLS

Mutual TLS — both sides of a connection prove who they are, not just one.

DaemonSet

A workload guaranteed to run one copy on every node — how tools like Falco watch the whole cluster.

CVE

Common Vulnerabilities and Exposures — the public ID number given to a known security flaw.

OIDC

A standard way to prove identity that lets a pipeline or pod get a short-lived credential instead of a permanent password.

Compliance framework prioritization

Across client engagements, prioritize by how often a framework applies and how directly Kubernetes controls satisfy it — not by which one sounds most serious. SOC 2 and PCI-DSS show up in nearly every engagement with hard audit deadlines; HIPAA is just as serious but scoped to whichever clients actually handle PHI.

This is a control-mapping reference for engineering prioritization, not a certification or legal opinion — confirm actual audit scope with a qualified compliance officer or external auditor before relying on it.

Framework Applies when Kubernetes controls it depends on Priority
SOC 2 Type II Almost every client under a contractual security commitment Audit logging with retention, GitOps-based change tracking, periodic RBAC access reviews Tier 1
PCI-DSS v4.0 Client processes, stores, or transmits cardholder data Namespace-level tenant isolation, default-deny NetworkPolicies, etcd encryption at rest, quarterly access reviews Tier 1
HIPAA Security Rule Client handles Protected Health Information Runtime mutation detection (eBPF), least-privilege RBAC, encrypted node-to-node transit via mTLS, pod-level PHI access trail Tier 2
Remember
  • SOC 2 and PCI-DSS show up in almost every client project — treat them as the default, not the exception.
  • HIPAA only matters when a client's app actually touches real patient health data.
  • A written policy without a matching Kubernetes setting behind it doesn't count during an audit.

Architectural and operational foundations

You already have the shape of it: a brain and a set of hands. Now let's zoom in on how they actually talk to each other, piece by piece — pick whichever explanation below gets a new teammate or a non-technical stakeholder oriented fastest.

In plain terms

Picture a busy airport. The control plane is the tower: it doesn't fly anywhere, but it watches every plane, decides who lands where, and reroutes traffic the instant something goes wrong. The worker nodes are the airplanes — each one carries passengers (your application) along a route the tower assigned. If a plane breaks down mid-flight, the tower doesn't wait around; it dispatches a replacement so the passengers still arrive.

In engineering terms

Kubernetes is a distributed, declarative state engine. etcd holds the cluster's desired and observed state as a consistent key-value store. The kube-apiserver is the only component that talks to etcd directly, and it authenticates, authorizes, and admits every request that touches cluster state. The kube-scheduler and controller-manager reconcile desired state against reality. On each node, the kubelet watches the API server for pods assigned to it and drives the container runtime through the CRI to make that state real.

Cluster topology

A single request's lifecycle

A request rejected at any stage never reaches etcd — each stage is an independent security checkpoint, not a formality.

Component reference

Component Runs on Responsibility If it's compromised
kube-apiserverControl planeSingle entry point for every cluster read and writeFull cluster compromise — this is the highest-value target
etcdControl planeStores all cluster state, including SecretsEvery Secret in the cluster is exposed if unencrypted
kube-schedulerControl planeDecides which node runs each podAttacker can steer workloads onto a node they already control
controller-managerControl planeRuns reconciliation loops (Deployments, ReplicaSets, and so on)Attacker can silently scale, delete, or recreate workloads
kubeletEach nodeStarts and supervises containers assigned to its nodeNode-level compromise, limited to that node's workloads
kube-proxyEach nodeImplements Service networking rulesTraffic can be redirected or intercepted on that node
Remember
  • The control plane decides what should happen; the worker nodes do the actual work.
  • etcd is the cluster's memory — if it leaks, every Secret in the cluster leaks with it.
  • Every single request passes three checkpoints before anything is saved: who are you, are you allowed, does it pass the rules.
02

Core principles, two ways

Every hardening decision in this manual traces back to one of four ideas: trust nothing by default, expect any single layer to fail, grant the least access that works, and never patch a running container.

Zero trust networking

In plain terms

Even inside the school building, every classroom door stays locked. Being in the hallway doesn't get you into a room — you show your ID at each door, every time.

In engineering terms

Assume the network perimeter is already breached. Default-deny all pod-to-pod traffic with NetworkPolicies, then explicitly allow only what's needed. Authenticate service-to-service calls cryptographically with mTLS rather than relying on network location.

Defense in depth — the 4Cs

In plain terms

You don't protect a treasure chest with one lock. You lock the chest, put it in a locked room, inside a locked castle, behind a moat. A thief who beats one barrier still has three more ahead.

In engineering terms

Security is enforced independently at four layers — Cloud, Cluster, Container, and Code. A breach at one layer should never cascade into the rest.

Least privilege

In plain terms

A hotel keycard opens your room and the gym — not every room in the building. You're given exactly the access your stay requires, nothing more.

In engineering terms

Every ServiceAccount, Role, and human identity gets the minimum verbs and resources it needs, scoped to a namespace wherever possible. Wildcard RBAC rules (resources: ["*"]) are a standing liability, not a convenience.

Immutable infrastructure

In plain terms

If a vending machine breaks, you don't repair it on the sidewalk — you swap in a working one and send the broken one back to the factory.

In engineering terms

Never patch a running container. Rebuild the image, push it through the same scanned and signed pipeline, and roll it out as a new revision. Read-only root filesystems (readOnlyRootFilesystem: true) make in-place tampering structurally harder.

The 4Cs, nested

LayerA concrete control at this layer
CloudPrivate control plane endpoint; IAM roles scoped per workload rather than a shared node identity
ClusterRBAC least privilege, encrypted etcd, audit logging shipped off-cluster
ContainerMinimal base image, non-root user, read-only root filesystem, dropped Linux capabilities
CodeDependency scanning, SAST in CI, secrets never hardcoded in source
Remember
  • Trust nothing by default — prove identity every time, not just once at the front door.
  • Never rely on one wall. Stack independent layers: Cloud, Cluster, Container, Code.
  • Give every identity the smallest set of keys it needs — nothing extra, ever.
  • Don't repair a broken container. Replace it with a new, freshly scanned one.

Hardening the architecture

A vanilla cluster is optimized for getting started, not for staying safe. Each row below is a decision you make once, deliberately, before workloads go live.

Area Insecure default Production hardened state
Control planeAPI server accepts anonymous requestsSet --anonymous-auth=false; restrict the API server endpoint to a private network or allow-listed CIDRs
etcdSecrets stored as plaintext on diskEnable a KMS provider for envelope encryption at rest; restrict etcd's network access to control plane nodes only
NetworkAll pods can reach all pods, in every namespaceDefault-deny NetworkPolicy per namespace, then allow-list required paths; add a service mesh for mTLS where volume justifies it
Node and podContainers run as root, no admission checks on privilege escalationReplace deprecated PSPs with Pod Security Standards — enforce restricted in application namespaces, baseline as an interim step
Identity and accessBroad ClusterRoleBindings and long-lived static tokensNamespace-scoped least-privilege RBAC; OIDC for human identity; short-lived, audience-bound tokens
Secrets managementSecrets committed to Git or passed as plain environment variablesExternal secrets manager (Vault, cloud KMS) synced via an operator; mount as files, not env vars, to limit accidental logging
Supply chainAny image from any registry can be deployedAdmission-time enforcement of signed images (Sigstore/Cosign) from an allow-listed registry only
Audit and observabilityAudit logging disabled or kept only on the nodeAudit policy capturing Metadata level for all requests, RequestResponse for Secrets and RBAC changes, shipped to immutable off-cluster storage

Hardening by deployment model

The controls above apply everywhere. Where you host the cluster changes how you implement identity and network hardening specifically.

Deployment model Insecure default state Production hardened state
Self-hosted (vanilla) API server reachable from any network; etcd stored unencrypted on disk; nodes managed with ad hoc, undocumented configuration Bind the API server to a private network or VPN; enable a KMS provider for etcd envelope encryption; run kube-bench in CI and on a recurring schedule against every node
Google GKE Workload Identity Federation not yet enabled on Standard node pools; public control plane endpoint with no authorized-networks restriction Enable Workload Identity Federation for GKE on every node pool (Autopilot has it on by default) so pods authenticate to Google Cloud APIs without service account key files; run a private cluster with an authorized-networks allow-list
AWS EKS Public cluster endpoint; pods inherit the EC2 node's IAM instance profile permissions by default Restrict the endpoint to a private VPC or security-group allow-list; adopt EKS Pod Identity for new workloads on EC2 nodes — simpler trust policy than OIDC federation — and keep IRSA only for Fargate workloads or clusters still mid-migration

Pod Security Standards spectrum

Network segmentation, before and after

Before — flat network

After — default deny, explicit allow

Remember
  • Kubernetes ships wide open by default — hardening is something you must turn on yourself.
  • Restricted Pod Security Standard should be the normal setting, not the exception you reach for later.
  • A namespace with no NetworkPolicy is wide open — deny everything by default, then open specific doors.
  • Where you host changes how you manage identity: Workload Identity Federation for GKE, EKS Pod Identity for AWS.

Where AI changes the threat model

AI workloads on Kubernetes cut both ways: they introduce new attack surface, and they're increasingly the tool used to watch that surface.

Threats introduced by hosting AI/ML workloads

ThreatAttack vectorMitigation
Data poisoningUnvetted or compromised training data silently corrupts model behaviorTreat data provenance like a software supply chain — verify and pin sources
Prompt injectionA tool-using agent is manipulated through its input into executing unintended commandsSandbox inference workloads with gVisor or Kata Containers rather than the default runtime
Accelerator starvationA runaway or malicious job monopolizes GPU/TPU capacity cluster-wideResourceQuotas and LimitRanges scoped specifically to accelerator resources
Dataset exposureLarge training volumes are read/write by default and an attractive targetMount read-only where the workload doesn't need to write; encrypt at rest
Model exfiltrationTrained weights leave the cluster through an unrestricted egress pathEgress NetworkPolicies scoped to known model registries only

Using AI/ML to protect the cluster

CapabilityHow it worksHuman-in-the-loop constraint
eBPF anomaly detectionA lightweight model trained on normal syscall behavior flags deviations static rules would missAlerts route to a human; no automatic kill by default
Policy draftingHistorical traffic patterns are mined to propose least-privilege NetworkPoliciesAlways reviewed and merged by a human, never auto-applied
Drift detectionLive cluster config is continuously diffed against the GitOps source of truthAuto-revert only in pre-approved, low-risk namespaces
Incident triageSignals are correlated and summarized into a timeline for a responderContainment decisions stay human-approved until false-positive rate is proven over time

AI workload isolation boundary

Remember
  • AI workloads need the same sandboxing as anything else — plus GPU quotas so one job can't hog the whole cluster.
  • AI is great at spotting something unusual; a human should still approve any action that shuts something down.

Benchmarks, checklist, and tooling

Checklist, grouped by CIS Benchmark domain

1  Control plane components

  • Anonymous auth disabled on the API server
  • Insecure port disabled; only the secure port is bound
  • Admission plugins include NodeRestriction and PodSecurity

2  etcd

  • Client and peer connections require TLS
  • Secrets encrypted at rest via a KMS provider
  • Data directory permissions restricted to the etcd user

3  Worker nodes

  • Kubelet anonymous auth disabled
  • Kubelet client certificate rotation enabled
  • Kubeconfig file permissions restricted

4  Policies

  • No wildcard verbs or resources in any ClusterRole
  • Pod Security Standards enforced, not just audited
  • Default-deny NetworkPolicy present in every namespace

06

Shifting left: workflow automation

None of module 3's decisions hold if they depend on someone remembering to apply them by hand. These checkpoints don't have to run in this order — they run continuously, at different stages of the same pipeline.

1

Scan at build time

Every image build runs through a vulnerability scanner before it's pushed to a registry. Fail the build on critical or high severity findings rather than warning and continuing.

2

Enforce policy at the pull request

Validate manifests against your organization's policy set — no privileged containers, no missing resource limits, no host network access — using Kyverno or OPA/Gatekeeper in CI, before a human ever approves the merge.

3

Detect and respond at runtime

Falco watches live syscall behavior. On a high-confidence match — a shell spawned inside a container that never spawns shells, for instance — trigger an automated response that isolates the pod's network access and pages a human, rather than killing it silently.

Reference pipeline

name: gitops-secure-delivery
on: [pull_request]
jobs:
  security-audit:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout source
        uses: actions/checkout@v4

      - name: Validate manifests against policy
        uses: kyverno/action-validate@v1
        with:
          policy: policies/disallow-privileged-containers.yaml
          resource: deploy/production-manifests.yaml

      - name: Scan image for vulnerabilities
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: 'registry.internal/app:${{ github.sha }}'
          format: 'table'
          exit-code: '1'
          ignore-unfixed: true
          vuln-type: 'os,library'
          severity: 'CRITICAL,HIGH'

Keyless cloud authentication for the pipeline itself

The pipeline that deploys your cluster shouldn't hold long-lived cloud credentials as GitHub secrets — that's the same anti-pattern module 3 flags for workloads. GitHub's OIDC token lets the runner assume a short-lived cloud role directly. 

permissions:
  id-token: write   # required to request the OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      # AWS EKS — assumes a role via OIDC, no static access keys stored anywhere
      - name: Authenticate to AWS
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
          aws-region: us-east-1

      - name: Update kubeconfig
        run: aws eks update-kubeconfig --name prod-cluster --region us-east-1

      # Google GKE — same pattern via Workload Identity Federation
      - name: Authenticate to Google Cloud
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: projects/123456789/locations/global/workloadIdentityPools/github-pool/providers/github-provider
          service_account: gke-deployer@my-project.iam.gserviceaccount.com

      - name: Get GKE credentials
        uses: google-github-actions/get-gke-credentials@v2
        with:
          cluster_name: prod-cluster
          location: us-central1

      - name: Apply manifests
        run: kubectl apply -f deploy/production-manifests.yaml

Incident response runbook

SeverityTrigger exampleAutomated actionHuman action
CriticalShell spawned inside a pod that never spawns shellsIsolate pod network access immediatelyPage on-call now
HighUnexpected outbound connection to an unknown IPFlag and rate-limit egressReview within the hour
MediumConfig drift from GitOps source of truthOpen a ticket, no auto-revertReconcile by next business day
Remember
  • Scan the image, gate the pull request, watch the runtime — that's the order they happen in, not the order of importance.
  • Never put a long-lived cloud key in a CI pipeline. Use a short-lived, OIDC-based token instead.

Hands-on lab exercises

Reading about a tool and running it are different skills. Each lab below is self-contained, uses a free local cluster (kind), and has a concrete way to verify you actually did it — not just that you followed the steps. If you don't already have a local cluster running, start with Lab 0.

Lab 0 — do this first

Set up a local cluster

Objective: get the four tools every later lab depends on installed and working, once, before touching any security tool.

What you're installing and why:

  • Docker — runs the containers that make up your local cluster
  • kind — "Kubernetes in Docker," a real cluster that boots in under a minute
  • kubectl — the command-line tool you use to talk to any Kubernetes cluster
  • Helm — installs pre-packaged tools like Kyverno and Falco with one command instead of dozens of manifests

Install (macOS, via Homebrew):

brew install --cask docker
brew install kind kubectl helm

Install (Ubuntu/Debian Linux):

sudo apt-get update && sudo apt-get install -y docker.io
curl -Lo kind https://kind.sigs.k8s.io/dl/latest/kind-linux-amd64 && chmod +x kind && sudo mv kind /usr/local/bin
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl" && chmod +x kubectl && sudo mv kubectl /usr/local/bin
curl https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

Install (Windows, via winget):

winget install Docker.DockerDesktop
winget install Kubernetes.kind Kubernetes.kubectl Helm.Helm

Lab 1

Benchmark your cluster with kube-bench

Objective: run a real CIS Benchmark scan and read the results.

Prerequisites: the cluster from Lab 0, running.

kubectl apply -f https://raw.githubusercontent.com/aquasecurity/kube-bench/main/job.yaml
kubectl wait --for=condition=complete job/kube-bench --timeout=90s
kubectl logs -l app=kube-bench

Verify: run kubectl logs -l app=kube-bench | grep -c "\[FAIL\]". You've completed the lab when you can produce and explain that number — not when it reads zero.

Lab 2

Gate a build with Trivy

Objective: see a vulnerability scanner actually fail a build.

Prerequisites: Docker, and Trivy installed.

docker pull nginx:1.16
trivy image --severity CRITICAL,HIGH --exit-code 1 nginx:1.16 ; echo "exit code: $?"

docker pull nginx:1.27
trivy image --severity CRITICAL,HIGH --exit-code 1 nginx:1.27 ; echo "exit code: $?"

Verify: the older image should print exit code: 1 — this is the same check that would fail a CI pipeline. The current image should print exit code: 0.

Lab 3

Block privileged containers with Kyverno

Objective: watch policy-as-code actually reject a bad deployment.

Prerequisites: Kyverno installed on your kind cluster.

helm repo add kyverno https://kyverno.github.io/kyverno/
helm install kyverno kyverno/kyverno -n kyverno --create-namespace

kubectl apply -f https://raw.githubusercontent.com/kyverno/policies/main/pod-security/restricted/disallow-privileged-containers/disallow-privileged-containers.yaml

kubectl run bad-pod --image=nginx --overrides='{"spec":{"containers":[{"name":"bad-pod","image":"nginx","securityContext":{"privileged":true}}]}}'

Verify: the last command should be rejected with an admission error mentioning the policy name — not a running pod. If bad-pod starts successfully, the policy isn't enforcing yet.

Lab 4

Prove a default-deny NetworkPolicy actually works

Objective: a real before/after test of network segmentation, not a reading exercise.

kubectl create namespace netlab
kubectl run web --image=nginx -n netlab
kubectl run client --image=busybox -n netlab -- sleep 3600
kubectl exec -n netlab client -- wget -qO- --timeout=2 web
# expect: the nginx welcome page HTML

kubectl apply -n netlab -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
EOF

kubectl exec -n netlab client -- wget -qO- --timeout=2 web
# expect: this now times out

Verify: the second wget must fail. If it still succeeds, double-check the cluster was created with Calico as in Lab 0 — kind's default CNI would let this pass silently without enforcing anything.

Lab 5

Trigger and observe a Falco alert

Objective: see runtime detection catch a live, real event.

Prerequisites: Falco installed via Helm.

helm repo add falcosecurity https://falcosecurity.github.io/charts
helm install falco falcosecurity/falco -n falco --create-namespace --set driver.kind=modern_ebpf

# in one terminal, tail Falco's logs
kubectl logs -n falco -l app.kubernetes.io/name=falco -f

# in a second terminal, do the thing Falco watches for
kubectl exec -it -n netlab web -- /bin/sh

Verify: the log-tailing terminal should print an alert referencing a shell being spawned inside a container, naming the pod. That line is the entire point of module 6's runtime detection step made real.

This is the lab most likely to need troubleshooting on WSL2. Falco reads raw kernel events, and WSL2 runs a custom, Microsoft-maintained kernel — the older kernel-module driver won't build there at all. The modern_ebpf driver used above is Falco's current default and works via CO-RE on most kernels 5.8+, which gives it a real chance on WSL2, but it isn't guaranteed. If the Falco pod crash-loops or logs eBPF verifier errors, this one lab is worth running on a real Linux box, a cloud VM, or a managed cluster (GKE/EKS) instead — everything else in this guide stays the same either way.
